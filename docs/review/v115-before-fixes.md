## P1: исправить до выпуска

### R1. Заводской сброс обходит защиту системного диска

`usb_monitor.py:396–407`, `factory_reset()`.

Сброс перечисляет и удаляет всё содержимое выбранного назначения, без проверки физического диска, маркера и принадлежности к папкам `DeviceN`. При обновлении старой установки с ранее допустимым назначением `/home` или домашней папкой новое копирование будет запрещено, но сброс всё равно удалит посторонние файлы с правами службы.

В изолированном воспроизведении папка без маркера с файлом `personal.txt` была очищена: `entries=1`, `UNRELATED_LOST=True`.

Исправление: проверить и удержать каталог архива до изменения БД; удалять только принадлежащие приложению данные. Запрещённое назначение должно останавливать сброс.

### R2. Конфликтующий и устаревший ID принимается как достоверный

`usb_monitor.py:954–975`, `1011–1016`.

При конфликте LOG/DCIM код явно выбирает ID журнала. Если актуальный журнал не содержит ID или не читается, обход может принять старый журнал; ошибки декодирования игнорируются. Записи могут попасть в папку другого ID, после чего исходные видео удаляются как успешно сохранённые.

Три падения полного набора непосредственно подтверждают проблему: `test_conflicting_log_and_recording_ids_are_rejected`, `test_latest_log_without_id_does_not_reuse_older_id`, `test_unreadable_log_does_not_fall_back_to_recording`. Эти ошибки были и в опубликованном v1.15; их давность не делает кандидат готовым.

Исправление: отказ при конфликте, использование актуального журнала и явный отказ при его повреждении или ошибке чтения.

### R3. Разрешение извлечения не означает, что все задания остановились

`gui.py:91–98`, `959–970`; `usb_monitor.py:1559–1563`, `1700–1716`.

GUI учитывает только `scanning/copying`. Во время `identifying` worker читает LOG/DCIM, но интерфейс уже может разрешить извлечение. Не учитываются задания в очереди, монтирование и worker в ожидании возвращения карты. Ожидание возврата может закончиться новым монтированием после нажатия остановки.

Реальная функция `_is_busy` возвращает `False` для `identifying` и `detached`. Добавление одной строки состояния не закрывает очередь и ожидания.

Исправление: подтверждение остановки должно приходить от движка после завершения всех активных и ожидающих операций; ожидание возврата и новые задания должны подчиняться остановке.

### R4. Ошибка размонтирования скрывается

`usb_monitor.py:1453–1458`, `1741–1756`; `gui.py:965–970`.

`_unmount()` подавляет ошибки. После `umount: target is busy` вызывающая сторона всё равно публикует `stopped/done`, а GUI разрешает извлечение. Воспроизведение с `CalledProcessError(32)` подтвердило отсутствие ошибки или отрицательного результата у вызывающей стороны.

Исправление: возвращать и проверять результат размонтирования; не разрешать извлечение при ошибке. Чужие монтирования намеренно не отключаются, поэтому для них сообщение должно отдельно объяснять необходимость системного безопасного извлечения.

### R5. Обновление может прервать начавшееся копирование

`updater.py:261–266`, `178`; `install_native.sh:46`, `180–181`, `231`.

После второй проверки занятости установщик выполняет apt и заменяет файлы при работающем мониторе. Подключённая в этот промежуток карта может начать копироваться, затем `systemctl restart` оборвёт worker. Вторая проверка после скачивания есть и покрыта тестом, но она не исключает этот последующий промежуток.

Подтверждено путём вызовов; опасная установка на станции не выполнялась.

Исправление: согласованный запрет новых заданий, ожидание завершения текущих операций и замена приложения только после этого. Не заменять это ещё одной несогласованной проверкой маркера.

### R6. Python-установщик удаляет отдельный C# продукт

`install_native.sh:131–166`.

Безусловный `remove_bestcam_station()` запускает `apt-get remove -y bestcam-station`, отключает службы, удаляет unit-файлы и udev-правило, переименовывает каталог C# установки. Обычное обновление Python тем самым выполняет незапрошенную миграцию. Откат Python C# установку не возвращает.

Это противоречит действующим правилам независимых продуктов. Удаление C# нужно убрать из обычного установщика и вынести в отдельно разрешаемую миграцию.

### R7. Повреждение настроек сбрасывает пароль и остальные параметры

`gui.py:38–58`; `usb_monitor.py:420–436`.

Повреждённый JSON превращается в пустой словарь. `_get_exit_password()` затем устанавливает стандартный пароль и перезаписывает файл. Воспроизведение вернуло `exit`, в файле осталось только `{'exit_password': 'exit'}`. Две независимые реализации записи также теряют изменения друг друга: сохранение устаревшего снимка вернуло `backup_dest` с `new-disk` на `old-disk`.

Исправление: единая синхронизированная операция изменения настроек, атомарная замена файла, отдельная обработка отсутствия и повреждения. Повреждённый файл не должен молча отключать защиту доступа.

### R8. Повторный v1.15 не распространяет исправления автообновлением

`VERSION:1`, `updater.py:58`, `220–225`.

`needs_update('v1.15', 'v1.15')` возвращает `False`. Станции с уже установленной v1.15 не загрузят заменённый архив; станции с `.failed=v1.15` также его пропустят. Это блокер именно обычного распространения через автообновление, а не ручной переустановки.

Для публичного исправленного выпуска нужен новый тег семейства `v1.*`. До выпуска исходники должны быть зафиксированы в целевом коммите, а архив должен воспроизводиться из него. Нынешнее одинаковое VERSION не позволяет оператору отличить исходный релиз от пересборок.

## P2 и решения, которые нужны до окончательного допуска

### R9. Возобновление не продолжает уже остановленную карту

`gui.py:950–954`; `usb_monitor.py:1896–1903`, `1973–1992`.

После завершения остановленного worker карта остаётся в `known`. Снятие паузы меняет только bool, поэтому карта не попадает в новые задания. Изолированное выполнение monitor при постоянно подключённом `sdb1` дало единственный submit до остановки и ни одного после возобновления.

Тест `test_monitor_pause.py` проверяет старт уже в паузе и появление новой карты, но не переход «копирование → остановка → продолжение той же карты». Нужен отдельный учёт прерванных заданий и повторная отправка только этих устройств.

### R10. Очистка может удалить копию между копированием и удалением оригинала

`gui.py:169–172`, `798`; `usb_monitor.py:714–715`, `779–803`, `1736–1739`.

Копия получает исходное время записи. Видео возрастом 40 дней сразу подходит под очистку с порогом 30 дней. Воспроизведение порядка «копировать → очистить архив → удалить сохранённые оригиналы» удалило оба экземпляра без ошибки копирования. Очистка действительно выполняется параллельно с монитором, в том числе при запуске.

**Оговорка о требованиях:** если политика намеренно уничтожает любую запись старше порога, даже впервые принесённую, удаление обоих экземпляров соответствует этой политике. Без уточнения нельзя называть сам возрастной фильтр ошибкой. При этом интерфейс и операции должны согласованно различать сохранённую копию и запись, уже удалённую по сроку хранения. Для гарантии резервного копирования нужны синхронизация очистки и удаления оригиналов и проверка фактической сохранности копии.

### R11. Поиск многократно обходит одни и те же папки

`gui.py:1100–1109`.

Каждый сеанс из `backups` запускает отдельный `os.walk(dest_path)`. Файлы отсекаются через `seen_paths`, но обходы каталогов не отсекаются. При отсутствии совпадений 100 сеансов в одной папке вызвали ровно 100 обходов. История растёт во время эксплуатации; повторные поиски создают дополнительные потоки, а поколение запроса проверяется только при выдаче результата.

Исправление: уникальные пути каталогов до обхода и прекращение устаревшего поиска. Это подтверждённый источник роста нагрузки при поиске, но не доказанная причина прежнего зависания всей станции.

### R12. Ошибка заводского сброса не показывается из-за отложенной lambda

`gui.py:854–855`.

Отложенный callback использует переменную `e` после выхода из `except`. Python очищает её; вместо сообщения об исходной ошибке возникает `NameError`. Воспроизведение реального метода подтвердило это.

Исправление: передать сохранённый текст ошибки аргументом `root.after`.

## Ограничения проверки

- Рабочую станцию не трогали. Подключение/отключение физических карт, отключение питания, отказ диска и многосуточный прогон не выполнялись.
- `systemctl is-active` и отсутствие перезапусков не доказывают работоспособность GUI: launcher может ждать X11. Для выпуска нужна проверка фактического окна и работы монитора.
- В кандидате отсутствует описанный в актуальных инструкциях путь обновления с флешки. Это расхождение состава продукта нужно решить до подготовки пользовательского описания релиза; автоматически добавлять функцию в рамках ревью не следует.
- Корневые workflow разделяют стабильные Python `v1.*` и предварительные C# `v2.*`. Но они собирают Git-коммит, а не этот локальный каталог артефактов.
- В проверенном пути не найдено доказательства переполнения стека. Это не заменяет измерений памяти и длительной нагрузки на целевой системе.

## Проверки для допуска исправленного кандидата

1. Все тесты ID проходят; конфликт, повреждение и отсутствие актуального номера не ведут к копированию или удалению оригиналов.
2. Сброс не касается системного диска и посторонних файлов; повреждённый конфиг не сбрасывает пароль.
3. Полный цикл остановки проверен на работающей, ожидающей и переподключающейся карте; возобновление продолжает ту же карту без физического переподключения.
4. При EBUSY и незавершённых workers интерфейс не разрешает безопасное извлечение.
5. Очистка и копирование имеют согласованную политику хранения, без ложного сообщения об имеющейся копии.
6. Обновление блокирует начало новых операций до перезапуска; Python-установка не меняет C# продукт.
7. Исправления зафиксированы в целевом коммите; выбран новый тег `v1.*`; архив, SHA256 и VERSION согласованы и проверены повторно.

Разрешения на выпуск пока нет. Исправления, сборку окончательного кандидата и выкладку следует учитывать как отдельные действия; публикация и установка выполняются только после команды пользователя.
