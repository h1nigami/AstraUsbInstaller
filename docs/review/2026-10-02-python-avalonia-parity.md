# Перенос изменений Python в C#/Avalonia

Проверка от 2 октября 2026 года. Основа сравнения: `b120965` (`v1.17`),
история от первого каркаса Avalonia `996ec12`, текущие вызывающие пути
и исправления после ревью Python v1.15. Удаление разметки гнёзд в рабочем
дереве учтено отдельно. По следующему запросу пользователя найденные пробелы
перенесены в рабочую ветку `codex/csharp-parity`. Реализация ещё не опубликована
и не установлена на станции.

По GitHub API последние опубликованные релизы:
[Python v1.17](https://github.com/h1nigami/AstraUsbInstaller/releases/tag/v1.17)
от 30 сентября и
[C# v2.0.5](https://github.com/h1nigami/AstraUsbInstaller/releases/tag/v2.0.5)
от 15 сентября. Тег `v2.0.5` указывает на `d00a47d`, как и Python `v1.10`.
Изменения C# после этого тега есть в исходниках, но их наличие в установленной
программе требует отдельной проверки версии станции.

## Удаление разметки

Из C# удалены раздел настроек, кнопки сопоставления и снятия разметки,
`SlotRow`, `PortMap`, чтение адреса физического порта и связанные тесты.
Окно закрепляется за идентичностью носителя, без привязки к физическому
USB-гнезду. Перестановка регистратора не направляет его прогресс на чужую
плитку. Подсказка стойки исправлена, диапазон C# от 6 до 30 окон сохранён.

Старую таблицу `port_map` программа больше не читает и не создаёт.
Существующая таблица остаётся в базе; удаление пользовательских данных
для отключения функции не требуется. Исторические ТЗ и прототипы
в `docs/design` сохраняют описание прежних требований.

Основные файлы реализации: [OperationGuard](../../avalonia/AstraUsb/Services/OperationGuard.cs),
[ArchiveDirectory](../../avalonia/AstraUsb/Services/ArchiveDirectory.cs),
[Settings](../../avalonia/AstraUsb/Services/Settings.cs),
[MainWindowViewModel](../../avalonia/AstraUsb/ViewModels/MainWindowViewModel.cs),
[ArchiveSearch](../../avalonia/AstraUsb/Services/ArchiveSearch.cs),
[Diagnostics](../../avalonia/AstraUsb/Services/Diagnostics.cs).

После перемонтирования того же архива поиск разрешает сохранённый ключ БД
в актуальный файл. Несколько ключей одного физического файла объединяются,
важность учитывается по всем ключам, включая записи вне выбранного периода.
Новые сеансы сохраняют ключ относительно выбранного `BackupRoot`, поэтому
последующие смены mountpoint не создают незащищённые копии записи БД.
Произвольный суффикс `DeviceN` у другого архива не считается доказательством
принадлежности к выбранному носителю.

## Старые пробелы исходной сверки

Эти функции были в Python ещё до появления Avalonia:

- Назначение по UUID/serial и относительному пути, добавленное в `f7cec0d`.
  Python повторно находит выбранный диск после смены mountpoint.
  C# хранит только `BackupRoot`, а исключение диска архива из источников
  определяется текущим путём. Маркер предотвращает часть ошибочных записей,
  но сам выбранный диск заново не находится.
- Обнаружение носителей через sysfs после ошибки `lsblk` и таймаут процесса.
  Python использует `subprocess.run(timeout=5)` с fallback. C# сначала
  выполняет блокирующий `ReadToEnd`, затем `WaitForExit(5000)`; зависание до EOF
  этой проверкой не ограничено. Fallback перечисления отсутствует.
  Это сравнение кода; зависший `lsblk` на настоящей станции не воспроизводился.
- Применение новой папки архива и правил хранения после сохранения.
  `SettingsViewModel` меняет отдельный объект настроек, а `MainWindowViewModel`
  и `BackupService` продолжают использовать снимок, загруженный при запуске.
  До перезапуска новые задания идут в прежний `BackupRoot` с прежними
  `KeepDays` и `DeleteVideoAfterCopy`; опрос и индикатор тоже используют старое
  назначение. При этом `SaveStorage` сообщает об успешном сохранении
  без признака необходимости перезапуска. Python разрешает назначение
  заново перед новым заданием. Разделение объектов C# появилось
  в `f44ee08d` и `c269ca63`, срок хранения в `f7ae54b9`; все эти изменения
  уже входят в `v2.0.5`. `DeleteVideoAfterCopy` относится к собственной
  настройке C#, без прямого эквивалента в нынешнем Python-конфиге.

## Различия, которые не являются забытым переносом

- Python использует `releases/latest` и принимает только `v1.*`.
  C# выбирает подходящий `v2.*` из списка релизов. Это отдельные каналы.
  Выбор своего семейства, точного архива, SHA256, проверка службы и версии,
  откат и память о неудачном теге уже реализованы.
- Старые алгоритмы `.astra_id` и `.bestcam_id` заменены ID из данных
  регистратора. Возвращать их в C# не требуется.
- Исправления Tkinter, удаления Docker-установки Python и общего замка
  Python-идентификации не требуют буквального переноса в Avalonia.
  Чтение карты и базы в C# уже выполняется в фоне.
- Срок хранения C# определяется собственной моделью времени сбора;
  важные записи защищены от очистки. Изменять эту модель ради совпадения
  с Python без отдельного требования не следует.

## Порядок реализации

Сначала защита назначения и сброса, общая блокировка операций,
запрет стандартного пароля при повреждённых настройках и сохранение
отложенного спула, применение выбранного назначения и правил хранения.
Затем остановка и безопасное извлечение,
возврат карт и привязка состояния плитки к устройству. После них
диагностика, отмена старого поиска и применение числа окон без перезапуска.

Первый запрос включал удаление разметки и сверку. Следующий запрос разрешил
перенос перечисленных изменений в C#; результат приведён в начале отчёта.

## Границы проверки и сохранённые различия

- Физическая топология системного диска проверяется на Linux. На Windows
  удержание файлов и защита от подмены работают; прежнее предупреждение
  о системном диске не стало запретом всей физической топологии Windows.
- При переходе со старого `.deb` его прежние `prerm/postinst` могут выполниться
  до скриптов нового пакета. Обычный `install.sh` проверяет занятость до `apt`.
  Прямая установка через `dpkg` поверх старой версии не получает полной защиты
  от старых скриптов задним числом.
- Блокировка охватывает запуск внешнего системного проигрывателя. Время жизни
  уже запущенного проигрывателя управляется системой; отдельная копия большого
  видео для такого просмотра не создаётся.
- Положительное копирование на настоящий внешний физический Linux-диск,
  горячее отключение USB и работа systemd на станции пока не проверены.
  Контейнерные сценарии используют настоящие процессы и файловые операции,
  но подставные команды служб. Системный/виртуальный диск контейнера защита
  обязана отвергать.
