# Нативный сервисный USB регистратора A11 в Avalonia-станции

Дата: 24.09.2026. Согласовано с владельцем в диалоге.

## Зачем

Станция на Astra Linux должна сама читать и записывать настройки CMS-сервера регистратора A11, подключённого в сервисном режиме по USB. Свежий BestCam-viewer это умеет, но через 32-битный Windows-SDK `libusbctrl.dll` и отдельный x86-процесс. На Linux этот SDK не запускается, поэтому станция говорит с регистратором нативно через `libusb-1.0` (на станции есть `libusb-1.0.so.0.3.0`).

Протокол снят с `libusbctrl.dll` дизассемблером и подтверждён на живом устройстве (станция 192.168.0.41, 24.09.2026). См. память `a11-service-usb-protocol`.

## Протокол (факты, подтверждённые живьём)

Устройство: USB VID `0x4255` PID `0x0001`, vendor-класс, endpoint 0.

Транспорт, одна команда:
1. Control OUT: `bmRequestType=0x40, bRequest=0x5A, wValue=0xAA, wIndex=0`, data = кадр. Число записанных байт обязано равняться длине кадра.
2. Пауза ~200 мс.
3. Control IN: `bmRequestType=0xC0, bRequest=0x59, wValue=0xAA, wIndex=0`, читать в буфер 1024 байта, повторять, пока ответ не завершится на `0D 0A`.

Кадр: `7E | len16(LE, = длина payload + 3) | cmd16(LE) | 00 | payload | xor | 0D 0A`, где `xor` — XOR всех байт от `7E` до конца payload включительно.

payload любой команды = 6-байтный префикс-пароль сессии (заводской `000000`) + данные команды.

Команды: вход `0x01` (данных нет), чтение сервера `0x0D`, запись сервера `0x0C`. У чтения и записи ответ несёт ту же команду.

Внутренний обменный формат SDK — 256-байтная структура: тип (int32, `2`=CMSV6) по смещению 0, признак включения (int32, `1`) по 4, IP-строка ASCII по 52 (0x34, 32 байта), порт uint16 по 84 (0x54). Те же смещения использует `CmsSettings` в viewer.

⚠️ Не подтверждено и подлежит реверсу: точная сериализация «256-байтная структура → payload кадра `0x0C`» и разбор «payload ответа `0x0D` → структура». Живой ответ `0x0D` показал, что раскладка кадра на проводе отличается от 256-байтной структуры (в кадре шли `тип, enable, два доменных слота, IP-строка, порт`). Запись без точного воспроизведения этой сериализации опасна — исторически кривая USB-запись ломала регистраторы. Поэтому реверс `SaveServerInformation` (`0x1004ece0`) и `ReadServerInformation` (`0x1004b630`) — отдельная первая задача, эталоны: сама DLL и живой A11.

## Состав

Новый код в `avalonia/AstraUsb/`, отдельными файлами, каждый с одной ответственностью:

1. `Services/ServiceFrame.cs` — чистый кодек: сборка кадра из (cmd, payload), разбор ответа (проверка `7E`, длины, XOR, `0D 0A`, извлечение payload), (де)сериализация 256-байтной структуры сервера ↔ payload кадров `0x0D`/`0x0C`, патч IP и порта в структуре (по образцу `CmsSettings.Configure`). Без libusb и без Avalonia. Полностью под юнит-тестами: эталонные векторы — снятые живьём ответы LOGIN и SERVER.
2. `Services/ServiceUsb.cs` — транспорт libusb-1.0 через P/Invoke: поиск устройства `4255:0001`, `Login`, `ReadServer`, `WriteServer`. Внешняя граница, заглушается в тестах вьюмодели через интерфейс `IServiceUsb`.
3. Интеграция в существующий фоновый поток обнаружения USB (`UsbWatcher`/сервис мониторинга): при появлении сервисного A11 станция логинится, читает настройки, и если адрес сервера не целевой — пишет и перечитывает (авто, паритет с viewer). Статус и ошибки — в `ActionLog`, видны на сервисной панели.

## Целевой адрес

Адрес CMS-сервера станция берёт из своей конфигурации (`Settings`) — станция связана с сервером объекта и знает его адрес; порт 6608, тип CMSV6, включение. Как именно адрес попадает в станцию от сервера объекта — отдельный этап (регистрация станции), в этом объёме адрес хранится в `Settings` (по умолчанию берётся из уже имеющегося у станции адреса сервера, если задан).

## Защита записи (обязательна)

- При нескольких подключённых A11 запись не выполняется: у входа нет однозначного выбора устройства (то же ограничение, что в viewer).
- Read-after-write: после записи настройки перечитываются и сверяются; расхождение — ошибка в журнал, не «успех».
- Guard: ответ длиннее ожидаемого отвергается, запись не выполняется (по образцу `CmsSettings.Payload`).
- Если прочитанный адрес уже целевой — запись не выполняется.
- ID устройства, MAC и прочие поля структуры сохраняются: пишется правка по месту (IP + порт + тип + включение), остальное из прочитанной структуры.
- Пароль сессии (`000000`) в коде не хранится строкой в UI; передаётся как байты команды.

## Проверка

- Юнит-тесты кодека (xUnit, как в проекте): сборка/разбор кадра, XOR, отказ на битом кадре и на превышении длины, круг «структура → payload → структура», патч IP/порта не трогает соседние поля. Эталон — живые ответы LOGIN/SERVER.
- Сборка `dotnet publish -r linux-x64 --self-contained`, весь набор тестов `dotnet test`.
- Валидация на живом A11 (станция 192.168.0.41): чтение совпадает с эталоном; запись в тестовый адрес и read-after-write; проверка отказа при двух устройствах — по возможности.
- ⚠️ Сохранность настроек после перезагрузки регистратора viewer'ом не подтверждена; после первой записи проверить перезагрузкой и повторным чтением, прежде чем считать путь рабочим.

## Выкат на станцию и уборка

Станция 192.168.0.41 сейчас на Python-версии (`astra-usb-monitor.service`). Для валидации Avalonia-сборка ставится `avalonia/install_native.sh` (он глушит Python-сервис и ставит `astra-usb-avalonia`). После проверки — вернуть Python-версию и убрать Avalonia-службу, как просил владелец. Резервные копии Python-версии на станции уже есть (`/opt/astra-usb-monitor.before-*`).

## Вне рамок

- Wi-Fi через USB (viewer умеет; здесь только CMS-сервер, пока владелец не попросит).
- Автополучение адреса сервера станцией от сервера объекта (регистрация станции).
- Прочие команды SDK (кодеки, GB28181, FTP регистратора и т. п.).
