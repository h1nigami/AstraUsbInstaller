# Astra ID как единый идентификатор устройства

## Цель

Обе версии станции должны одинаково определять устройство. Единственным
постоянным идентификатором становится положительное целое число из файла
`.astra_id` на носителе. Номер из прошивки, имя записи, USB-серийник и старый
`.bestcam_id` не могут заменить Astra ID.

## Что привело к изменению

В клиентском видео показаны два регистратора с нанесёнными номерами `64001` и
`64002`. После подключения станция успешно копирует данные, но на основном
экране показывает только номера отсеков и состояние. Связь между регистратором,
его Astra ID и архивной папкой оператору не видна.

В выбранном архиве при этом находятся папки `Device1`, `Device2`, `Device3`,
`Device5` и `Device9`. По их названиям нельзя понять, какой из подключённых
регистраторов создал конкретную папку. В именах записей остаётся заводской номер
камеры, поэтому просмотр содержимого тоже не объясняет эту связь. Клиент также
показал, что старые папки `Device*` нельзя удалить из файлового менеджера.

Эти симптомы появились не из-за одной ошибки отображения. В проекте сложились
несколько конкурирующих идентификаторов:

- Python хранит числовой ID в `.astra_id` и использует его для папки
  `Device{id}`.
- Ранний алгоритм пытался узнавать носитель по USB-серийнику, хотя эта модель
  отдаёт одинаковый заводской серийник на разных регистраторах.
- После исправления одинаковых серийников Python начал выдавать новый Astra ID
  носителю без маркера, но при одновременном дубликате `.astra_id` молча
  перенумеровывает второй носитель.
- Avalonia ввела отдельный `.bestcam_id` формата `BCU-01-0001` и стала считать
  его удостоверением камеры. Старый `.astra_id` при обычной загрузке остался в
  стороне, хотя архивная папка всё равно строится по локальному числовому
  `devices.id`.
- Пользовательское имя и номер из прошивки показываются как подписи, но не
  объясняют, какой числовой ID использован в `Device{id}`.
- Обе Linux-службы запускаются от `root`, поэтому созданные ими каталоги могут
  оказаться недоступны владельцу рабочего стола.

Ранее мы сохраняли стабильное имя `Device{id}`, потому что абсолютные пути уже
записаны в базе и используются поиском, очисткой и очередью отправки. Само это
решение остаётся правильным. Ошибка была в том, что две версии по-разному
отвечали на вопрос, откуда берётся `id`, а интерфейс скрывал ответ от оператора.

Новая схема устраняет именно это расхождение. Нанесённый на корпус номер,
заводской номер в имени файла и пользовательское имя остаются описаниями. Они
не определяют папку и не могут переписать Astra ID.

## Источник номера

Локальный SQLite `devices.id INTEGER PRIMARY KEY AUTOINCREMENT` является
счётчиком станции. Если на новом носителе нет `.astra_id`, станция создаёт
строку `devices`, получает следующий локальный `id`, записывает его в
`.astra_id` и перечитывает файл для проверки. До успешной проверки копирование
не начинается.

Если носитель уже содержит корректный `.astra_id`, используется именно этот
номер. Если соответствующей строки в локальной базе ещё нет, она создаётся с
тем же `devices.id`. USB-серийник сохраняется только как диагностическая
метаинформация и не участвует в выборе устройства.

Пустой или повреждённый существующий `.astra_id` считается ошибкой. Станция не
должна молча заменить такой файл и связать носитель с другой историей.

## Разрешение конфликтов

Если `.astra_id` и другой идентификатор указывают на разные записи, побеждает
`.astra_id`. Приложение не переписывает его заводским или программным номером.

Если два одновременно подключённых носителя содержат одинаковый `.astra_id`,
второй носитель получает понятную ошибку. Автоматически выдавать ему новый
номер нельзя: это нарушило бы правило источника истины и могло бы скрыть
дубликат карты.

## Переход Avalonia со старого маркера

Avalonia сначала ищет `.astra_id`. Старый `.bestcam_id` используется ровно
один раз и только для безопасного перехода:

1. Если `.astra_id` уже есть, `.bestcam_id` игнорируется при идентификации.
2. Если `.astra_id` отсутствует, а `.bestcam_id` однозначно связан с записью в
   локальной базе, в `.astra_id` записывается локальный `devices.id` этой
   записи. Имя камеры и назначенный сотрудник сохраняются.
3. Если подходящей записи нет, номер выдаёт локальный SQLite-счётчик.
4. После появления `.astra_id` старый маркер остаётся только совместимой
   метаинформацией и больше не выбирает устройство.

Python уже использует `.astra_id`, но перестанет перенумеровывать носитель при
обнаружении дубликата. Вместо этого копирование второго носителя завершится
ошибкой без изменения маркера.

## Папки и интерфейс

Архивная папка остаётся `Device{astra_id}`, например `Device1`. Это сохраняет
существующие пути в базе и не требует опасного переноса накопленных файлов.

На основном экране обеих версий показывается `Astra ID 1`. Если оператор задал
имя, оно отображается рядом как дополнительная подпись, например
`Astra ID 1 · 64001`. Поэтому номер на экране однозначно соответствует папке
`Device1`, а нанесённый на корпус номер больше не подменяет идентификатор
архива.

## Доступ к архиву

Linux-службы работают от `root`, поэтому после копирования они передают папки
устройства владельцу и группе корневой папки архива. При запуске это же
исправление применяется к существующим папкам `Device*`. Другие каталоги в
корне архива не затрагиваются. На Windows сохраняется штатное наследование
ACL.

## Проверки

Тесты должны подтвердить:

- `.astra_id` побеждает USB-серийник, `.bestcam_id` и номер из записи;
- новый носитель получает следующий локальный `devices.id`;
- Avalonia переносит известный `.bestcam_id` в `.astra_id` без потери записи;
- дубликат активного `.astra_id` не перенумеровывается;
- ошибка записи маркера останавливает копирование и автоудаление;
- основной экран показывает Astra ID во всех раскладках Avalonia;
- папка называется `Device{astra_id}`;
- исправление владельца ограничено папками `Device*` внутри выбранного архива.

После локальных проверок изменения выпускаются раздельно: Python `v1.9` как
стабильный релиз и Avalonia `v2.0.4` как предварительный релиз. В каждом релизе
остаются только файлы своего продукта и соответствующие SHA256.
