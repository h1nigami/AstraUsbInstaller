# Версия из релизов и автообновление киоска

Дата: 01.09.2026
Ветка: `claude/version-and-auto-update`

## Зачем

Киоск стоит на точке без обслуживания. Сейчас он не знает своей версии и не
умеет обновляться: `update.sh` требует каталог `.git`, а установка из релиза
GitHub его не содержит — там только автоархив исходников. Значит любая точка,
поставленная из релиза, остаётся на той версии, с которой её привезли.

Нужно, чтобы программа показывала свою версию и сама подтягивала новые релизы,
когда сеть есть, и молча продолжала работать, когда сети нет.

## Решения, принятые до проектирования

- Обновление ставится **полностью автоматически**, без человека у экрана.
- Источник — **GitHub напрямую**. Репозиторий публичный, `releases/latest`
  отдаёт ответ без токена, поэтому на киоске не хранится никаких секретов.
- При неудачном обновлении — **автооткат** на предыдущую версию.
- Docker не используется: только нативная установка через `install_native.sh`.

## Устройство

### Файл VERSION

Единственный интерфейс между релизом и программой. Лежит рядом с `gui.py`
(после установки — `/opt/astra-usb-monitor/VERSION`), одна строка:

```
v1.1 2026-07-17
```

Тег и дата публикации релиза, разделённые пробелом. Руками файл не правится
никогда: его кладёт релизный workflow, а на машину он попадает вместе с
остальными файлами приложения.

Читают файл двое: GUI — чтобы показать версию, и апдейтер — чтобы понять, надо
ли обновляться. Если файла нет или строка не разбирается, GUI пишет «Версия не
определена» и работает дальше. Приложение не должно падать из-за версии.

Для установки из git-клона (у разработчика) `install_native.sh` при отсутствии
`VERSION` пробует получить тег через `git describe --tags` и записать файл сам.
Не вышло — ставится без версии, это не ошибка.

### Релизный workflow

Новый `.github/workflows/release.yml`, срабатывает на публикацию релиза:

1. Берёт тег и дату публикации, пишет `VERSION`.
2. Собирает `astra-usb-monitor-<tag>.tar.gz` с полным составом приложения
   (то же, что и в автоархиве, плюс `VERSION`).
3. Считает `sha256`, кладёт рядом файл `.sha256`.
4. Прикрепляет оба к релизу как ассеты.

Апдейтер качает именно этот ассет, а не автоархив: только у него внутри есть
`VERSION`, и только для него есть контрольная сумма.

### Апдейтер

`updater.py` в каталоге приложения плюс два systemd-юнита:

- `astra-usb-update.service` — тип `oneshot`, запускается от root,
  `ExecStart=/usr/bin/python3 /opt/astra-usb-monitor/updater.py`.
- `astra-usb-update.timer` — первый запуск через 10 минут после загрузки,
  дальше раз в 6 часов, с `Persistent=true`, чтобы пропущенный за время
  выключения запуск не потерялся.

Отдельный юнит выбран не ради красоты. `install_native.sh` в конце делает
`systemctl restart astra-usb-monitor`, и если бы обновление шло изнутри GUI,
этот рестарт убил бы процесс ровно посреди подмены файлов — точка осталась бы
с наполовину обновлённой установкой. Таймер живёт в собственном cgroup и
рестарт переживает. По той же причине он работает, когда GUI вообще не
стартует, а это как раз тот случай, ради которого нужен откат.

Порядок работы:

1. Прочитать `VERSION`. Файла нет — считаем, что версия неизвестна, и
   обновляемся до текущего релиза.
2. Запросить `https://api.github.com/repos/h1nigami/AstraUsbInstaller/releases/latest`
   через `urllib` с таймаутом 15 секунд.
3. Сравнить теги **на неравенство**, а не «больше — меньше». Точка приводится
   к тому, что помечено на GitHub как latest; отозванный релиз тогда лечится
   публикацией предыдущего, а не выездом на объект.
4. Проверить простой (см. ниже). Занято — выйти до следующего раза.
5. Скачать ассет и `.sha256`, сверить сумму. Не сошлась — выйти, ничего не
   трогая.
6. Распаковать во временный каталог.
7. Скопировать текущий `/opt/astra-usb-monitor` в `/opt/astra-usb-monitor.prev`
   (прошлая копия перед этим удаляется).
8. Запустить `install_native.sh` из распакованного каталога.
9. Подождать минуту и проверить, что сервис жив.
10. Не жив — откатиться.

Любая сетевая ошибка — недоступный DNS, таймаут, ответ не 200 — приводит к
тихому выходу с записью в journal. Для точки без интернета это холостой цикл
раз в 6 часов, и ничего больше.

### Что меняется в install_native.sh

Установщик остаётся единственной точкой развёртывания, и обновление — это тот
же установщик, запущенный из свежего архива. К тому, что он делает сейчас,
добавляется:

- `VERSION` и `updater.py` копируются в каталог приложения наравне с
  `gui.py`, `usb_monitor.py`, `main.py` и `start_native.sh`;
- если `VERSION` в исходниках нет, но есть `.git`, файл собирается из
  `git describe --tags` и даты коммита тега;
- ставятся и включаются `astra-usb-update.service` и `.timer`.

Каталог `data/` установщик не трогает, как и раньше, — база, настройки и
маркер занятости переживают обновление.

### Как понимается «простой»

GUI обновляет время файла `data/.copying`, пока среди задач есть хотя бы одна
в состоянии сканирования или копирования. Апдейтер считает точку занятой, если
файл существует и моложе минуты.

Признак «есть ли подключённые флешки» не годится: диск назначения тоже сидит на
USB и подключён постоянно, а флешка, забытая в порту после копирования,
блокировала бы обновления навсегда. Маркер отвечает ровно на нужный вопрос —
идёт ли прямо сейчас запись. Если GUI упал и маркер не обновляется, точка
считается свободной, что и требуется.

### Откат

Через минуту после установки апдейтер смотрит `systemctl is-active` и счётчик
`NRestarts`. Сервис не активен или счётчик растёт — значит новая версия падает
на старте: удаляем каталог приложения, возвращаем `.prev` на место,
перезапускаем сервис и пишем в journal, что откатились.

Критерий грубый. Если графической сессии нет, `start_native.sh` честно ждёт её
в цикле, и сервис при этом считается живым — сломанный GUI так не отловить. Но
главный сценарий он ловит: релиз, на котором Python падает при импорте или на
старте.

## Отображение номера вместо DeviceN

Задача, с которой началась работа, и она независима от всего остального.

Подпись устройства собирают два хелпера: `_friendly_device_label`
(`usb_monitor.py:488`) и его двойник в `gui.py:747`. В обоих запасной вариант
`f"Device{id}"` заменяется на номер. Плюс подпись поля «Device ID» и три
сообщения в диалогах.

Сборка пути к папке (`gui.py:1113`) не трогается. Имена папок на диске
записаны в `backups.dest_path` у всех прошлых копий, и переименование оборвало
бы поиск и выгрузку по ним.

## Проверка

Юнит-тестами на Windows покрывается то, что не требует Linux и сети: разбор
`VERSION`, выбор нужного ассета из ответа GitHub (на сохранённой фикстуре),
решение «обновляться или нет», определение занятости по времени файла. Загрузка
подменяется в тестах.

Всё остальное — установка, таймер, откат, поведение без сети — проверяется
только на живой Astra Linux. Для этого на док-станции (192.168.0.41) нужен
доступ по SSH; сейчас порт 22 закрыт.

## Что сознательно не делаем

- Сравнение версий по semver. Равенство с latest решает задачу.
- Выбор произвольной версии для отката — только предыдущая.
- Прогресс обновления в интерфейсе. Обновление идёт в простое, показывать его
  некому.
- Альтернативный источник обновлений. На точках есть интернет.
- Подпись пакета. HTTPS и `sha256` закрывают битую закачку и подмену в канале.
- Сборка бинарника. Системные утилиты он не заменяет, а в режиме замкнутой
  программной среды Astra неподписанный файл не запустится.
